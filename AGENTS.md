# rebuild-review

Claude Code plugin: a one-shot review that rebuilds a full project from its behaviour and
what it renders, then scores the rebuild against the original. See README.md.

## Install and test

- Install: `claude plugin marketplace add MehdiMamas/rebuild-review`, then `claude plugin install rebuild-review@rebuild-review`.
- Run: `/rebuild-review:rebuild-review <target-path>`. It makes `<target>-rebuild-review/<run-id>/` next to the target and starts the workflow `rebuild-review:rebuild-review-run`. Phases not described below are stubs that write `<Phase>.done`; finished phases are skipped on a rerun with the same run folder.
- Unattended: `scripts/unattended.sh <target> --max-usd N [--base url@ref|none|keep] [--run-dir dir] [-- claude flags]` (#79): sets `CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS=0` and `CLAUDE_CODE_DISABLE_BG_SHELL_PRESSURE_REAP=1` (#101: under memory pressure Claude Code otherwise stops the background work while the session idles; cap memory from outside, e.g. systemd MemoryMax), passes `unattended=1` so the skill never asks, refuses without a limit.
- Validate: `claude plugin validate .`
- Test without installing: `claude -p "/rebuild-review:rebuild-review <path>" --plugin-dir <this checkout> --permission-mode bypassPermissions`, against a throwaway git repo; its `git status` must stay clean.
- Gotcha: the skill and the workflow must not share a name. With both called `rebuild-review:rebuild-review`, the call goes straight to the workflow and the skill text never runs.
- Gotcha: a clean `CLAUDE_CONFIG_DIR` has no login, so `claude -p` cannot run there; use `--plugin-dir`.

## Rerun from a phase

- `node scripts/rerun.mjs <runDir> --from Parity|Score|Report [--no-build]` (#145; skill args `runDir= from= noBuild=1`; `unattended.sh --run-dir D --from P [--no-build]`). Removes `<Phase>.done` for that phase and later ones, moves old results to `<runDir>/previous-<n>/` (`parity/` results except `tests`, `areas`, `removed`, `untested*.md`; `golden-rebuild/`; `score/`; `report/` incl. `stopped.txt`; for `--from Score` only `score/` and `report/`, for `Report` only `report/`) all-or-nothing, appends a `phase` event. `rounds.json` moves, so the loop starts at round 1. `project/`, `rebuild/`, `golden/`, `events.jsonl`, `cost.json`, `size.json` stay.
- Refuses with exit 2 and no change when `Rebuild.done`, `project/rebuild-run.json`, `run.json`, `features.md` or `golden/` is missing (`parity/parity.json` too for Score and Report), or a `long/<name>.pid` is alive with no `.exit`.
- `--no-build` writes `NoBuild.done` (removed by a rerun without it). The workflow reads it with the other `.done` files, so a resume keeps it: the Estimate block is skipped and the parity loop writes `loop-stop.txt` "not rebuilt: NoBuild.done is set" instead of building. A plain resume keeps it; a rerun without the flag clears it. Test: `node --test scripts/rerun.test.mjs` (its phase list must equal `PHASES` in the workflow).

## Capture (web adapter)

- Contract every adapter follows: `adapters/CONTRACT.md`. Web adapter: `adapters/web/` (`capture.mjs`, `probes.mjs`, `context.mjs`).
- Package manager: pnpm 12.16.1 (pinned in each `package.json` `packageManager`; `benchmark/app` and the electron fixture stay npm, they are the apps under test). Install it with `npm install -g pnpm@12.16.1` or `corepack enable`. Electron's postinstall is allowed in `adapters/electron/pnpm-workspace.yaml`.
- Setup: a run does it first (`scripts/adapter-deps.mjs` runs `pnpm install` in each `adapters/*` whose dependencies are missing; a failure stops the run with the reason). By hand: `cd adapters/web && pnpm install`. Chromium must be installed (`pnpm exec playwright install chromium`). Test: `node --test scripts/adapter-deps.test.mjs`.
- Run: `node adapters/web/capture.mjs --app <runDir>/run.json --out <runDir>/golden [--states states.json]`. The app must already be cloned to `<runDir>/work/`; `run.json` is described in the contract. Only localhost addresses are accepted.
- Test: `cd adapters/web && pnpm test` (about 3 minutes). It runs seven numbered checks on a `bench:init` copy of `benchmark/`, never on the repo folder, and prints which planted defects the probes flagged.
- `startApp` (`adapters/web/app.mjs`) stops a leftover of the app on the run's port when the listener's working folder is inside the run's work copy (agents exploring the app can leave one); any other listener, a missing `lsof` or Windows still refuses. Test: `node --test scripts/app-env.test.mjs`.
- Gotcha: `work/` holds source, so the sandbox for the rebuild step (#7) must deny reads of it as well as the target.
- Sign-in (#144): `run.json` `auth: { steps, expect? }` (`adapters/web/auth.mjs`); the session is in memory only, stand-in values only; `states.json` states stay signed out. `endsSession` / `endsSessionPath` in `context.mjs` are the one rule for controls never pressed (crawl buttons, `input[type=submit|button]` and links, probe clicks): whole-word log out / sign out, and when signed in also delete / close / deactivate account; `LOGIN_RE` in `auth.mjs` matches a sign-in path segment only. Without `expect`, signed in needs the page to have left the sign-in form (another route, or the password field gone) as well as a stored session. `adapters/web/redact.mjs` masks every typed value of any length as a whole value (`test` leaves `latest`), in every text file capture writes (render.html, a11y.json, HAR) and in `events.mjs`; `scripts/room.mjs` `filterGolden(src, dest, authValues)` masks again in the builder's copy. Coverage: `screensCapturedWithSession` (every screen captured with the session, public ones too, not only those that need it), `refusedSignedIn` (401/403 while signed in). `scripts/room.mjs` `copyEnv`/`dropEnv` handle `env` and `auth` apart. Parity tests and finders are not signed in yet.
- Test: `cd adapters/web && node --test test/auth.test.mjs` (runs capture against `test/site-auth.mjs`, several minutes, needs Chromium; run it on `pc` with `xvfb-run -a`).

## Capture (Electron adapter)

- `adapters/electron/` (`launch.mjs`, `capture.mjs`, `parity.mjs`); contract and driving notes: `adapters/CONTRACT.md`, `adapters/electron/DRIVING.md`. `run.json` has no `address`; it has `launch: { executablePath?, args, schemes? }`.
- Setup once: `cd adapters/web && pnpm install` (the electron adapter reuses its probes and axe-core), then `cd adapters/electron && pnpm install` (Electron and Playwright; Linux needs a display, `xvfb-run -a`).
- Run: `node adapters/electron/capture.mjs --app <runDir>/run.json --out <runDir>/golden [--states states.json] [--max-screens N] [--max-buttons N] [--max-har-bytes N]`. Screens are found by clicking; the app is relaunched and the clicks replayed to get back to one, so a run takes minutes.
- The app runs isolated: own user data, home and environment (an allowlist, never this process's), outside requests from a window blocked and listed, the main process sent to a dead proxy, native dialogs answered "canceled" and listed. Requests over a custom protocol handled in the main process are invisible to the driver, so the app's own data should come over loopback or `file:`.
- Test: `cd adapters/electron && pnpm test` (about 30 minutes: fourteen checks on `test/fixture`, which plants six problems and one clean screen, a custom scheme, a click that closes the window and one that replaces it, a helper window that opens first and closes itself after 300 ms, and a `run.env` value; `test/answers.json` is read only by `test/run.mjs`). Misses are printed as MISS, never tuned away. CI job `electron-adapter` runs it under `xvfb-run`.
- `run.env` is applied to the app too (after the allowlist copy; the isolation variables and dead proxy still win). A click that closes the window or reloads the app into a new one is not a crash: the probe group becomes a row in `golden/probes-not-checked.json` (`{probe, route, reason}`, reason "the window closed or reloaded after the click") and a `<probe> <route>: <reason>` string in `manifest.json` `notCaptured`; `measureScreens` does the same per screen. The web capture writes the same file.
- Linux preflight (`adapters/web/libs.mjs`, `linuxLibs`, shared with the web adapter): before the first launch `ldd` is run on the Electron binary; missing libraries are fetched with `apt-get download` and unpacked with `dpkg -x` into a cache under the temp folder (300 MB cap, never sudo) and added to `LD_LIBRARY_PATH` for the app. A library with no entry in the package map, no `apt-get`, no network or a failed download stops the run with the library names and the first error line. Test: `node --test adapters/web/test/libs.test.mjs`.
- Run it headless on Linux, never on a desktop Mac (the windows disturb the user): on the `pc` machine, clone the branch into `~/work/rebuild-review-electron`, `pnpm install --frozen-lockfile` in `adapters/web` and `adapters/electron` (with `PLAYWRIGHT_SKIP_BROWSER_DOWNLOAD=1` for web), then `HOME=$(mktemp -d) xvfb-run -a pnpm test` in `adapters/electron`. Missing system libraries (libnss3, libnspr4) can be unpacked with `apt-get download` + `dpkg -x` and given through `LD_LIBRARY_PATH`, which the adapter passes to the app. Bring back only the log.
- A rebuild must stay on the original's platform; the workflow stops with a plain reason otherwise.

No dependencies; `cd adapters/cli && pnpm test` (about 40 seconds, light, no display) runs eight checks on `test/fixture` (a to-do tool with five planted problems); `test/answers.json` is read only by `test/run.mjs`. ## Capture (backend adapter)

- `adapters/backend/` (`api.mjs`, `discover.mjs`, `capture.mjs`, `probes.mjs`, `parity.mjs`, `worker.mjs`); contract: `adapters/CONTRACT.md` section "Backend", driving notes: `adapters/backend/DRIVING.md`. `run.json` is `{platform: "backend", dir, install, build, start, address, openapi?, readyPath?, env?}`. No dependencies (Node 24 `fetch`); `cd adapters/backend && pnpm test` (nine checks, about 4 minutes: hung routes wait 10 s each).
- Run: `node adapters/backend/capture.mjs --app <runDir>/run.json --out <runDir>/golden [--states states.json] [--max-screens N]`. A screen is one operation plus one state; operations come from the OpenAPI document, else by probing. Each screen is captured twice; JSON values that differ become `"<varies>"`.
- `api.mjs` has its own start and stop (not the web adapter's `startApp`): the service needs an allowlisted environment, a fresh temp home at every fresh start, and on Linux a network namespace that only the call helper (`worker.mjs`, run through `nsenter`) can reach. Elsewhere (proxy mode) raw connections are not blocked, and `notCaptured` says "network: proxy mode, raw connections not blocked". A fresh restart also empties the work copy: untracked files that were not there after the build are deleted and tracked files go back to how the build left them (a `git stash create` commit taken after the build, else `git checkout -- .`; never in the target). Only a child that has not emitted `exit` is signalled by its process group; `RR_NSENTER` replaces the `nsenter` command for the helper-exit test.
- Parity tests start the service themselves through `API_MODULE` (`prepare`, `call`, `restart`), because namespace ports are not reachable from the test; `parity.mjs` runs them with `--test-force-exit` and kills the service groups it listed.
- A store outside this machine (Postgres, Redis on another host) in `run.env` is refused. Windows is refused.
- `scripts/room.mjs` `filterGolden` needs nothing special for a backend golden; `scripts/room.test.mjs` has a test for it.

## Inventory phase

- Needs `<runDir>/work/` (clone of the target) and `<runDir>/run.json` (platform, install, build, start, address); `golden/` is used when present. The skill passes `pluginRoot` (`${CLAUDE_PLUGIN_ROOT}`) so the workflow can run `scripts/check-features.mjs`.
- Four finders run in parallel on sonnet (code reader, black-box user, history reader, docs reader), each writing only `<runDir>/inventory/<finder>.md`; the black-box user also writes `inventory/states.json`. Then merge and a critic loop (at most 3 rounds).
- Writes `<runDir>/features.md` (IDs, given/when/then, seen by, keep or defect), `<runDir>/technology.md` (languages, frameworks, storage, build tools) and `<runDir>/Inventory.done`. `features.md` and `technology.md` hold no source: `node scripts/check-features.mjs <file> <work>` must pass for each (fences, source paths, import/JSX lines, 40+ char copied runs that contain code); the phase fails if it does not after 2 fix tries.
- Tests: `node --test scripts/check-features.test.mjs`; for the full phase, run the workflow on a `bench:init` copy (clone it to `<runDir>/work`, write `run.json`, `Capture.done`), then `node benchmark/score-inventory.mjs <runDir>/features.md`. Only the scorer reads `answers.json`.
- Each run gets its own port from `scripts/free-port.mjs` (capture writes it into `run.json`; the finders start the app with `PORT` set to it).
- If the second capture fails, run the skill again with the same run folder: `InventoryFound.done` makes it skip the finders, merge and critics and repeat only the capture. Test: `node --test scripts/free-port.test.mjs`.

## Parity phase (phase 1: the suite)

- Needs `features.md`, `run.json` and `golden/`. Adapter entry point: `parity.mjs --app <run.json> --tests <dir> --out <results.json>` (contract in `adapters/CONTRACT.md`); a platform with no `parity.mjs` stops the phase with a plain reason. Web: `adapters/web/parity.mjs`, app start and stop shared with capture in `adapters/web/app.mjs`.
- A writer agent (sonnet) writes `<runDir>/parity/tests/F-xxx.test.mjs`, one per feature, from `features.md` and the running app, never from `work/`. `keep` tests assert the behaviour, `defect` tests assert the Intended text and should fail on the original. A fix loop (3 rounds) repairs wrong tests; two runs on the original must agree. Tests that stay wrong or flip move to `parity/removed/` and are listed in `parity/untested.md`.
- With `<runDir>/project/rebuild-run.json` it also runs the tests on the rebuild (`parity/rebuild.json`), captures it into `golden-rebuild/` and runs `scripts/visual-diff.mjs` (`parity/visual-diff.json`, percent of differing pixels, no pass or fail). Writes `parity/parity.json` and `Parity.done`.
- Parity loop (phase 2): with a rebuild, `runParity()` runs the suite on it, then `node scripts/parity-results.mjs loop <parDir> <features.md> <runDir>` decides in code: it appends `{round, build, failing, costUsd}` to `parity/rounds.json`, writes `parity/failures.md` (one `## F-xxx (keep|defect)` section per failing tested feature, failure message only: no stack lines, absolute paths hidden, 15 lines at most; the builder never sees test code) and prints `{action, reason, failing}`. `done` when nothing fails; `stop` on `no progress` (a round, from the second on, whose failing count is not lower than the lowest before it; #143), `suite did not run` (no `run-error.txt` and every failing feature reads `no result for this feature`; no build is started from it), `budget` (`LOOP_USD` = 50 spent on builds) or `rounds` (`MAX_ROUNDS` = 5); otherwise `build`: `room.mjs build --failures parity/failures.md` (the child's budget is `min(BUDGET_USD.build, LOOP_USD - spent)`; none left fails with `budget`). The new project replaces `project/` only if the child succeeds; the old one is kept as `rebuild/project-from-build-<n-1>`. On a stop, if the last build is not the one with the fewest failures (ties go to the later build), that build's project is moved back and the suite is rerun so `rebuild.json` matches what ships. The reason for a stop or failed build goes in `parity/loop-stop.txt`; stopping with failures is not a phase failure, they stay in `parity.json`. A rebuild that will not start (`parity/run-error.txt`) makes every tested feature fail with that text.
- `failures.md` carries the test's assertion message (the writer prompt asks for one on every assertion, saying what was expected and what was seen); a bare `assert.ok` failure gets the line "The test gave no message for F-xxx; read its text in features.md." (`noMessage` in `scripts/parity-results.mjs`).
- Prep for each suite run on the rebuild is code (#140): `parity-results.mjs prep <parDir> <rebuild-run.json>` deletes `rebuild.json` and `run-error.txt` and gives a web rebuild a free port in `address`. A prep failure throws a Parity phase error with its reason; only a non-zero exit of the adapter's `parity.mjs` writes `run-error.txt` (`parity-results.mjs run-error`) and reads "the rebuild would not start".
- Layout-shift probe (web): the early snapshot records only elements the user can see (`checkVisibility` with opacity and visibility; empty boxes skipped), so content hidden until data loads is not a shift (#86). Test: `cd adapters/web && node --test test/layout-shift.test.mjs`.
- Probe `script-cost-per-key` (web): script time per keystroke in every visible text input (up to 5) at 4x CPU slowdown; the value is `script-ms-per-key` in `golden/timings.json`, flagged above 16 ms. The threshold is not tuned to the fixture.
- Pass or fail decisions are code: `scripts/parity-results.mjs` (`wrong`, `settle`, `merge`); `features.md` entries start `F-xxx keep.` or `F-xxx defect.`. Tests: `node --test scripts/parity-results.test.mjs scripts/visual-diff.test.mjs` (the latter needs `cd adapters/web && pnpm install` first); `cd adapters/web && pnpm test` checks the timing is written and prints it.

## Stack and Rebuild phases (clean room)

- Both run through `node scripts/room.mjs stack|build --target T --run-dir R [--failures file]` (started by `longRun`, then a sonnet agent reads the result file named on the last output lines, `<runDir>/rebuild/<mode>-<n>.result.json`). Prompts: `prompts/stack.md`, `prompts/build.md`. `Stack.done` / `Rebuild.done` are written only when the result says ok. `--failures` is for the parity loop (#8).
- In stack mode `stack.md` is checked with `check-features.mjs` right after the child writes it; on problems the child is asked up to two times to rewrite it (`fixStack`, transcripts `stack-<n>.fix-<i>.jsonl`), and it is copied to the run folder only after it passes.
- The room is a new `mktemp -d` folder outside the run folder (the run folder's name contains the target's name). Everything the builder sees is a filtered copy in `room/input/`: `features.md`, `technology.md`, `stack.md` and `golden/`. `features.md`, `technology.md` and `stack.md` are re-checked with `check-features.mjs` before copying, and the copies are grepped for the target path and the run folder path.
- `golden/` is filtered (`filterGolden`) because `network.har` holds the app's JS, CSS and source map bodies and `render.html` can hold inline scripts, which together are the source. JSON, image and font bodies stay (API contract and assets); `run.json` is dropped.
- The child is `claude -p` in the room with `--setting-sources project` and the settings file passed with `--settings` (kept in `<room>.settings/`, outside the room, because it names the denied paths), no user settings or memory, WebFetch/WebSearch off, `--no-session-persistence`. Permission mode `bypassPermissions`; the wall budget and the models are constants at the top of `room.mjs`; stack and build budgets come from `size.json`.
- Settings gotchas, proven by `scripts/room.live.test.mjs`: a Read deny rule needs the absolute form `Read(//abs/path)` (one slash is ignored); the Read tool is stopped only by that deny rule, Bash only by `sandbox.filesystem.denyRead`, so both are needed; `sandbox.network.strictAllowlist: true` is required or the model can widen the network list itself with `allowed_domains`.
- The child may not read the target, the run folder, the folder holding all runs (`<target>-rebuild-review`), the git common dir of a worktree target, the plugin root, `~/.claude/projects` and these credential folders when present: `~/.ssh`, `~/.aws`, `~/.gnupg`, `~/.config/gh`, `~/.netrc`, `~/.npmrc`, `~/.docker`. `Edit` rules (which cover Write) stop writes to the target and run folder.
- The built project is delivered with `git clone` of its committed state (it must be a clean git repo with a commit); ignored and uncommitted files never arrive.
- Every run first proves the wall: a canary in `<runDir>/.canary`, a haiku child tries to read it; a hit, a sandbox that cannot start, or a child that never tried a `cat` and a Read refuses the build. After the run, any target or run folder path in the child's transcript fails it.
- Tests: `node --test scripts/room.test.mjs` (CI, no `claude`); `node --test scripts/room.live.test.mjs` (local, calls `claude`, costs money).

## Score phase (phase 1: measure, judge, compare)

- Needs `project/rebuild-run.json` and `parity/parity.json`; otherwise the phase stops with a plain reason. Files: `rubric.json` (gate and weights), `scripts/score.mjs`, `prompts/{judge,skeptic,compare}.md`, `adapters/web/metrics.mjs` (LCP, CLS, bytes, heap, narrow overflow, axe-core; written by `capture.mjs` into `timings.json` and `a11y-violations.json`).
- Every score is a comparison: a metric delta is `(original - rebuild) / max(original, rebuild)` for lower-is-better (flipped for higher), from -1 to +1, positive means the rebuild is better; a difference under the metric's `floor` (absolute, or `"10%"` of the larger side) counts as 0; a metric missing on either side is "not measured", never 0. A value is the mean of its measured deltas and its judged delta (judges' `(rebuild - original) / 10`), half each. Overall is the weighted sum, -100 to +100. Functionality is a gate (`minPassRate` 0.95 on the rebuild's parity run), reported beside the scores, never blended in.
- Code does the arithmetic. Three blind judges (sonnet) each get `judge-<i>/A` and `/B` in a temp folder with shuffled labels (no `.git`, `README*`, `run.json`, `rebuild-run.json`, `stack.md`); the label map is written to `score/.labels.json` only after judging. Each judge writes `answer.json` in its own folder; `score.mjs check <answer.json> <judgeDir> <score/judge-N.json>` writes only the kept items to `score/judge-N.json` (dropped ones beside it as `.dropped.json`), so a judge with no checked file counts for nothing, and the first prep step clears `score/`. It drops any score whose citation is not a real file, `file:line`, or metric name for that side. Skeptics look at each judged gap of 3+ points and each metric delta of 0.5+; a refuted judged gap is removed and listed, a measured number is only annotated. `score.mjs collate` writes `score/score.json`; a compare agent writes `score/compare.md`.
- `files`, `lines` and `longest-file` count the same files as `size.mjs` (`skipReason`): no lock, vendored, generated or non-source files, so a long markdown spec or a JSON file does not move them.
- Change weights or floors in `rubric.json` only; no code reads them as constants. Never tune them to make a fixture pass.
- Compatibility is narrow: accessibility violations and horizontal overflow at 390 px, Chromium only. The output says "other browsers: not checked".
- Tests: `node --test scripts/score.test.mjs`; `cd adapters/web && pnpm test` (check 3c prints the new timings).

## Report phase

- Files: `scripts/report.mjs` (`verdict`, `check-actions`, `render`), `prompts/{compare,actions}.md`, `rubric.json` key `verdict` (`adoptOverall` 15, `worseValue` -0.15, `betterValue` 0.15, from phase 1's same-against-same noise limits; never tune them to a fixture). Writes `report/index.html` and `Report.done`.
- Code decides the verdict: `adopt` (gate passed, overall >= adoptOverall, no value delta <= worseValue), `port` (not adopt, some value delta > 0.15), else `leave`; no score is `leave`; a gate with no rate (no parity test ran on the rebuild) is `none`, shown as "no verdict", and `benchmark/calibrate.mjs` refuses to record it (#141). A sonnet agent only proposes `report/actions.proposed.json` (`evidence: [{kind: metric|file|shot|feature, ref}]`); `check-actions` drops any action with a false citation (listed in `actions.dropped.json`).
- The page is one file: no script, strict CSP, images embedded (at most 6 pairs and 8 MB, the rest counted), every string escaped. `compare.md` must use `## <value>` with `### was`, `### now`, `### should`. `parity/rounds.json` and `parity/loop-stop.txt` are optional.
- The report is private: the skill publishes it with the Artifact tool when present and the target is not sensitive; otherwise only a `file://` link.
- Tests: `node --test scripts/report.test.mjs`.

## Score phase (phase 2: the rebuild beats the original)

- Checker: `node benchmark/score-rebuild.mjs <runDir> [--out file] [--control]`. It starts the original (`run.json`) and the rebuild (`project/rebuild-run.json`) one after the other with `startApp`, runs every planted-problem check on both and prints a table: item, original, rebuild, evidence. Exit 0 only if the original has every item and the rebuild has beaten every one. `--control` checks only the original (every D, H and B item must read `present`).
- Written from `answers.json` but black-box: controls are found by role and label, slow and failed requests are made with `page.route`; bloat (B1 to B4) is read from the source files; D1 multiplies the list response to 2000 rows with `page.route`, types 5 keystrokes into the search box at 4x CPU slowdown and compares script ms per key (present above 16 ms; gone at or under 16 ms or 50% lower than the original). If the original does not read above 16 ms under that load, D1 is `could not check` on both sides.
- Results are `present`, `gone` or `could not check`; the last never counts as beaten. Beaten means `gone` for D and B items, `present` for H items (features that must survive).
- Never tune the checker, `rubric.json`, tests or prompts to get a pass; an item the rebuild does not beat is reported with its cause.
- `score.mjs blind` flips the label order for each judge after the first, so both orders occur in every run. Test: `node --test scripts/score.test.mjs`.

## Confidence

- `node scripts/confidence.mjs <runDir>` writes `score/confidence.json`; `report.mjs render` computes the same and shows it in the verdict section, with a table of the parts and each part's inputs, and a percentage for each value. Settings are in `rubric.json` key `confidence` (first guesses, never tune them to a fixture).
- The number is the weakest of four parts, each 0 to 100: **coverage** (features compared out of found, metrics measured out of expected, screens reached out of seen when `golden/coverage.json` exists, multiplied), **agreement** (spread of the judges' per-judge mean deltas in `values.<name>.judges`, share of judged gaps refuted, share of judge items dropped), **margin** (distance of overall and each value from the verdict thresholds in units of noise; on a threshold reads about 50), **track record** (Wilson lower bound of the share of right verdicts in `benchmark/calibration.json`, so few runs give a low number). The report names the part that set it. No score reads "not measured". A target with more source lines than the biggest calibrated run is capped and the page says so.
- Record a known-answer run: after Score, `node benchmark/calibrate.mjs <runDir> --expect adopt|port|leave --kind same|worse|fixed`. Write the expected verdict on the issue first. A wrong verdict stays in the file; never change thresholds, prompts, weights, tests or the fixture to fix it.
- The parity tests for known-answer runs are `benchmark/known-answer-tests/` (F-001..F-007 are the planted defects D1-D7, F-008..F-011 the hidden features H1-H4); run them with `adapters/web/parity.mjs --tests benchmark/known-answer-tests`, and set `PLAYWRIGHT_PATH` when the tests are copied elsewhere. On the unchanged fixture the defect tests fail, so the gate fails and the verdict is `leave`; a copy with every defect fixed passes.
- It is not a calibrated probability. Reading it: a low number with "track record" as the limit means the tool has few checked runs, not that this verdict looks bad. Tests: `node --test scripts/confidence.test.mjs`.

## Same settings on both sides, and rules from the first real run (#11)

- `run.json` may hold `env` (object of stand-in settings, never real secrets). `startApp` starts the app with `{...process.env, ...run.env, PORT}`. `scripts/room.mjs` copies `env` into `project/rebuild-run.json` right after the build is delivered (`copyEnv`; nothing is added when `run.json` has none) and removes it from the copy the builder gets on a `--failures` run, so the builder never sees it. Values are never printed or put in the report. Tests: `node --test scripts/app-env.test.mjs scripts/room.test.mjs`.
- Prompt rules in `workflows/rebuild-review.js` (asked, not enforced): the merge step lists docs-only items under `## Not built (from the docs)` as bullets without an F-id (no new kind; `kinds()` ignores them); a defect about what the running app does must record what was done and seen, and the critic repeats it once; the parity test writer asserts meaning not wording, does not assert browser behaviour, and stays inside the feature's text.

## Workflow syntax

- `workflows/rebuild-review.js` is one script of long template literals, so a plain backtick in a prompt breaks every run. `node --test scripts/workflow-parse.test.mjs` compiles it; CI runs that.
- No prompt asks an agent to run a command in the background (`run_in_background`): `workflow-parse.test.mjs` fails on any. Every capture, parity and `room.mjs` step goes through `longRun(name, command, label, phase)`: one cheap agent runs `node scripts/long-run.mjs start <runDir>/long <name> -- <cmd>` (a detached supervisor; output in `<name>.log`, `<name>.exit` written when it ends; the same name still running is attached to, not started twice), then the script asks one cheap agent at a time to run `long-run.mjs wait <dir> <name> --seconds 540` once in the foreground (Bash timeout 600000) until it prints `exited` (with the code) or `lost` (no exit file and a dead supervisor), at most 54 waits (8 hours). Workflow code decides; no agent waits. Test: `node --test scripts/long-run.test.mjs`.
- A top-level `claude -p` run of the workflow needs `CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS=0`, or the workflow itself is stopped after 10 minutes.

## Conventions

- Releases: bump `.claude-plugin/plugin.json` in a PR, merge it, then tag that merge commit `v<version>`. The `tag` workflow (`scripts/tag-version.mjs`) fails a tag whose version differs from `plugin.json`. Test: `node --test scripts/tag-version.test.mjs`.
- Contributing: see CONTRIBUTING.md for setup, the checks CI runs and how to file a bug.

- Any kind of project, not only web. Nothing outside a platform adapter may assume HTML,
  a browser or React; a platform-specific need means the adapter contract changes.
- In and out: the words and what the app renders are the input. The output is the full
  project done the best way, backend included. The score and report come with it and never
  replace it. Never call the rendered app "output" in docs or issues.
- The plugin must install on its own from this repo. claude-sync-data only lists it, and
  nothing here may depend on claude-sync, session-manager or other mods.
- Rules that must hold are enforced by the workflow script or file layout, not by asking
  the model nicely. The main one: the rebuild agent cannot read the target's source.
- A target project is never modified. Every run writes to its own output folder.
- No Claude or AI attribution in commits, PRs or release notes.
- This repo is public. Issues, comments, PRs and commits never name a private app reviewed with this tool or show what it does (its routes, its domain words; write a route as `/items/<id>`), and hold no local paths, machine state or process ids. Every helper brief says so. A leak is deleted and reposted clean, never edited.
- Agents that start the app stop it by process id (`STOP_APP` in the workflow); never `pkill` or `killall`. `startApp` stays the guard for one left behind (#65).

## Size and scale (#35)

Test: `node --test scripts/size.test.mjs`.
- `capture.mjs` takes `--max-screens` (30), `--max-buttons` (10), `--max-per-route` (2) and `--max-har-bytes` (50 MB) and writes `golden/coverage.json`: screens reached, screens cut, `sameRouteSkipped` (`[{route, count}]`), buttons skipped, HAR entries dropped. The crawl (`adapters/web/crawl.mjs`: `routeKey`, `pickNext`, `leftOver`) turns UUID, all-digit and 8+ hex path segments into `:id`, visits every route not yet visited before a repeat of one, and visits at most `--max-per-route` URLs of one route; the rest are `sameRouteSkipped` (a sampling choice, listed in `notCaptured`), and `screensCut` holds only routes the screen cap stopped. Test: `node --test adapters/web/test/crawl.test.mjs`. `cd adapters/web && pnpm test` check 8 covers it.
- Estimate: `size.mjs <workDir> <runDir> [--max-usd N]` exits 3 and prints "Nothing was spent" when N is below the high estimate or missing; the workflow runs it first and stops with `Estimate` as the stopped phase. The skill prints the range and asks for `maxUsd` first.
- `room.mjs` (stack, build) and `parity-results.mjs loop` read their budgets from `size.json` via `readPlan(runDir)`; with no `size.json` they get the floors (stack 3, build 25, loop 50). The loop budget counts the first build too, so `loopUsd` is `buildUsd` plus the fix-round money (`perUnit.loopUsd` per unit, at least 25) (#74). `room.mjs` adds each run's spend to `<runDir>/cost.json` (phases `Stack`, `Rebuild`; agent costs outside the room are not in it).
- Tests: `node --test scripts/size.test.mjs scripts/parity-results.test.mjs`. Never run `node --test scripts/*.test.mjs`: it includes `room.live.test.mjs`, which calls `claude` and costs money; use the file list in `.github/workflows/ci.yml`.

## Areas (#35 step 3)

- `scripts/areas.mjs`: a big app (more than one size unit) is split into areas inside the run; a small one gets the single area `all` from code (`areas.mjs init`), with today's prompts and files. For a big app a sonnet agent reads `areas.mjs tree` (paths and line counts, no contents) and writes `<runDir>/areas.json` `{areas:[{id,paths,entry}], exclusions:[{path,reason}]}`; `areas.mjs check` refuses unless every counted source file is in exactly one area or one exclusion with a reason (3 fix tries, then the run fails). Skipped files (lock, vendored, generated, not source) need no area.
- Inventory per area: finders, merge and critic run in parallel per area into `inventory-areas/<id>/`; `areas.mjs renumber` joins them into `features.md` with global `F-xxx` and an `[area: id]` tag on each entry; then one dedupe pass across areas (merged-away IDs listed in `inventory-areas/dedupe-merged.txt`) and `areas.mjs ids` proves every entry still has a tag. Per-area `states.json` are joined with `areas.mjs states`; per-area technology notes are joined into `technology.md`. A finished area is marked by `areas.mjs mark <runDir> <id>`, which writes `inventory-areas/<id>.done` holding the sha256 of that area's entry in `areas.json` (paths and entry); `areas.mjs done <runDir>` prints the ids (JSON array) whose marker matches the current entry and whose `features.md` and technology file exist, the workflow skips those, and a changed entry, a missing output file or a deleted marker reruns the area. `trackedTexts` caches the raw tracked file texts in `<tmp>/rebuild-review-texts-<uid>/` by folder and HEAD when tracked files are unchanged (folder 0700, files 0600, used only when the folder is a real folder owned by this user and each file a regular file owned by this user, none written over 256 MB, a file that does not parse is deleted and the texts read fresh; 2 GB cap, oldest removed first, never the file just written, `.tmp` files older than an hour removed, also when the write fails); the CLI and `room.mjs` share it.
- Parity per area: one writer per area (`areas.mjs ids <runDir> <id>` gives its features), writes `parity/untested-<id>.md` (joined by `areas.mjs untested`) and its marker `parity/areas/<id>.done`; a finished area is skipped on rerun and a feature whose test file exists is not rewritten.
- Tests: `node --test scripts/areas.test.mjs` (generated 450,000-line fixture, no model calls). The workflow itself is only checked for syntax; the prompts have not been run.

## Rebuild per area (#35 step 4)

- With more than one area, `room.mjs stack` appends a note asking `stack.md` for two sections: "Build order" (a list, one item per area starting with its ID, every area once; `areas.mjs buildOrder` parses it and the stack step fails if it is wrong) and "Shared contracts".
- `room.mjs build` then runs one builder child per area, in that order, in the same room and its one git repo. Each child gets its area's features (the `[area: id]` tags in `features.md`), the stack and the contracts. The wall is proven once before the first child; the transcript check runs after every child. The pool is the build budget (`buildUsd`); each child may use what is left of it.
- A finished area is committed, cloned into `project/` and recorded in `rebuild/areas-done.json`; a rerun builds only the areas not done (the room starts from the committed `project/`). A budget that runs out before an area fails with `budget`.
- Parity loop rounds (`--failures`) go only to the areas that have failing features (feature IDs from `failures.md`). One area behaves as before.

## Score per area and coverage (#35 step 5)

- With more than one area, every blind judge answers once per area (the task names the area; its features are the `[area: id]` entries of `features.md`). Answers are checked into `score/areas/<id>/judge-<j>.json`; skeptic ids carry the area (`<area>.j0-3`). Measured numbers (`lines`, `lcp`, ...) are whole-app and listed once.
- `score.mjs collate` weighs the per-area totals by counted lines of the original (`areaWeights`, from `areas.json` and `work/`), writes `areas` (id, lines, weight, overall, value deltas) into `score.json` and the weighted `values` and `overall`. The gate is still the whole rebuild's test pass rate. One area (no `areas.json`, or one area): the old code path runs, so the arithmetic is exactly today's.
- `weigh` also weighs `values.<name>.judges` (each judge's mean delta, judge k of each area weighted by lines), so `confidence.mjs` agreement still sees the judges on a multi-area score. Test: `scripts/score.test.mjs`.
- `areas.mjs coverage <runDir>` (first step of Report) writes `coverage.json`: per area files, lines, features, tested, run on rebuild, passing, whether it was built; the excluded list; screens reached or cut (`golden/coverage.json`); and `notReached` (areas not rebuilt, features with no test, screens cut, buttons skipped, HAR entries dropped). `report.mjs render` shows it as the Coverage section. This feeds #36 (confidence).
- Tests: `scripts/areas.test.mjs` (a generated 450,000-line fixture through areas, parity, score and the report page; no model calls).

Files: `check.mjs`, `check-result.mjs` (status and exit code), `loadProbes`/`clickProbes` in `probes.mjs` (`runProbes` still calls both for capture, same rows).

A thrown error in a probe group becomes `notChecked` (never a fail); uncaught errors exit 3.

The browser starts with `--disable-gpu --disable-software-rasterizer` (WebGL off) and takes one throwaway screenshot first; screenshots time out after 15 s (#95).

Test: `node --test adapters/web/test/browser.test.mjs`.
- Probe `safe-area` (#121): `loadProbes` (so `check.mjs`, not capture) adds a row per route and mode (`<id>:browser`, `<id>:standalone`) at 390x844 with iPhone insets; it fails on a control that cannot leave the top 47 or bottom 34 px of a `viewport-fit=cover` page, or one covered at its centre (on-screen controls only). Fixed or sticky controls (or inside an inner scroller) are judged where they sit at load; in-flow controls, on or off screen, are clear if some scroll position puts them between the insets (`SAFE_EVAL`; `html`/`body` overflow is the document scroll, hidden or clip means no scroll). `safeAreaProbes` runs it alone. Test: `cd adapters/web && node --test test/safe-area.test.mjs` (CI runs it).
- Safe-area fallback (#137): after load the probe reads `env(safe-area-inset-top|bottom)`; if either differs from the emulated 47/34 (a Chromium that takes the CDP override but does not feed `env()`), it rewrites every `env(safe-area-inset-*)` use in readable stylesheets and inline styles to the emulated px, waits two frames and judges, and the row says `env() insets not applied by this browser; rewrote N env() uses ...` (plus `M stylesheet(s) unreadable`). A linked sheet is replaced by a `<style>` copy of its rules. `noInsetOverride` skips the CDP call and is for tests only.
- Gotcha: a test that serves from the test process cannot use `spawnSync` on the command; the server blocks with it. Run the server as a child process.
- Not counted as a data request by the fault probes (`isDataRequest` in `context.mjs`): prefetches (`sec-purpose`/`purpose` containing prefetch, `next-router-prefetch`), `rsc` requests without `next-action`, and `/_next/data/` paths. A slow client navigation with no feedback is therefore not flagged.

## Upstream base and foundations (#70)

- `node scripts/base.mjs detect <target> <runDir>` writes `<runDir>/base.json` `{kind: fork|framework|template|none, upstream: {url, ref, commit} | null, evidence, ownPaths, ownLines}`, all from code: a git remote named `upstream`, merge commits from another remote, a `repository` in package.json or Cargo.toml that is not the project's own remote, vendored trees (submodules, `third_party` or `vendor` folders with their own license), and the newest commit of the upstream that HEAD builds on. Own code is every tracked file that is not in that commit or differs from it. It runs on the target (the run's `work/` clone has no `upstream` remote), before `size.mjs`, so the estimate is for own code. Nothing found is `none`.
- The skill asks once (keep the detected base, give `url@ref`, or `none`) and saves it with `node scripts/base.mjs pin <runDir> <url@ref|none>` as `run.json` `base` (`"none"` or `{url, ref}`); a pinned answer wins. Only https, http, git, ssh and file addresses are accepted. The capture prep step keeps an existing `base` key.
- Own lines are changed lines against the base (#72): `base.mjs` `changedLines` (git numstat, added plus deleted, binary and skipped files 0; a file new on top of the base counts all its lines); `detect` writes `ownLineChanges` (path to n) and `ownLines` is their sum. `size.mjs` sizes by it, and `score.mjs measure --own-run` uses it for `lines` on both sides (rebuild: since the first commit of `project/`); `files` and `longest-file` stay whole-file. A run with no base is unchanged.
- Own code only: `size.mjs` (`scan(workDir, own)`, `readOwn(runDir)`), `areas.mjs tree <workDir> <runDir>`, `check` and `coverage`, and the score code metrics `files`, `lines` and `longest-file` (`score.mjs measure ... --own-run <runDir> --side original|rebuild`; the rebuild side counts files changed since the first commit of `project/`, which is the base). Rendered metrics stay whole-app. Finders list behaviour that comes only from the base under `## From the base (not rebuilt)` as bullets without F-ids.
- `room.mjs` (`prepareRoom`, inputs include `base` for the build) fetches the upstream at the pinned commit in the plugin process (`fetchBase`: shallow fetch of that commit, hash compared), runs the wall check (`checkWall`: none of the target's own commits may be in the base, and no own path may exist there with the target's content; otherwise the build is refused with the reason), puts the tree without `.git` in `room/input/base/` and starts `room/project` as that tree in one commit. The upstream host is never added to the child's network list (`REGISTRIES` only). `baseNote` adds the prompt note: change only the app's own behaviour on top of the base.
- Foundations: a finder writes `<runDir>/foundations.md` with nine fixed sections (license and attribution, platforms and packaging, extension and plugin APIs, saved user data, settings and config files, external services, auth and accounts, telemetry and crash reporting, update channels and signing); every bullet is `found: ... (evidence: ...)`, `not found: ...` or `not applicable: ...`. `node scripts/foundations.mjs check <file>` refuses a missing section, a bullet with no status or a found item with no evidence; the finder gets 2 fix tries, then the phase fails; `check-features.mjs` runs on it too. The builder and stack steps get it in `room/input/`; `stack.md` says how each found item is kept.
- Report: a Base line in the verdict (upstream, commit, kind, how found), and a Foundations section. A sonnet agent proposes `report/foundations.proposed.json` (`[{item, status: kept|changed|missing, evidence: [{kind, ref}]}]`, item ids like `userdata.1`); `report.mjs check-foundations <runDir>` drops unknown items, bad statuses, no evidence and false citations (`evidenceProblem`, as `check-actions`) into `report/foundations.json` and `foundations.dropped.json`. A found item with no checked status reads "not checked", never "kept"; dropped entries are listed under what the run could not check.
- Tests: `node --test scripts/base.test.mjs scripts/foundations.test.mjs scripts/size.test.mjs scripts/room.test.mjs scripts/report.test.mjs scripts/areas.test.mjs scripts/score.test.mjs`. A real proof (a small public fork rebuilt on its base, the report naming the base) is run on the `pc` machine, headless.

## Watch page (#82)

- Files: `scripts/events.mjs` (`emit`, `read`; CLI `node scripts/events.mjs <runDir> phase|decision|cost|made '<json>'` appends to `<runDir>/events.jsonl`; strings cut to 500 chars, `run.json` env values replaced by `***`), `scripts/watch.mjs <runDir> [--port N] [--open]`. Events are written by the scripts that decide: `size.mjs` (estimate decision, cost in `addCost`, `maxUsd` stored in `size.json`), `base.mjs pin`, `areas.mjs check`, `parity-results.mjs` (`loop`, `settle`), `score.mjs check`, `report.mjs verdict`. The workflow script emits nothing: phase state comes from the `<Phase>.done` markers; a failed phase is a non-zero `long/*.exit` or `report/stopped.txt` (written by `report.mjs render --stopped`). `room.mjs` emits the wall decisions (`wall` and `base wall`, `held` or `refused`, fixed-sentence reasons with no paths): the canary proof, the base check and the transcript check after each child.
- Never bind anything but 127.0.0.1 (no host flag) and never drop the `?k=` token check. `/file` stays inside the run folder and refuses dotfiles, `work/ room/ project/ rebuild/` at any depth, `run.json`, `rebuild-run.json`, `*.settings*`, `long/` except `*.log`, and any type but png jpg webp log md json txt; logs are cut to the last 64 KB with run, target and home paths hidden. The page sets text with `textContent` only, under a CSP with a nonce.
- `watch.mjs` keeps its own copy of `PHASES`; `watch.test.mjs` fails if it differs from the workflow's. `watch.pid` in the run folder stops a second server; the server exits 30 minutes after `Report.done` or a stop.
- A `report/stopped.txt` older than any `<Phase>.done`, `events.jsonl` or `long/*.log` is ignored (`stopText`): a rerun continues in the same folder, so a stop that was recovered from neither marks the page stopped nor starts the 30-minute exit timer.
- A run that stops at the estimate (`size.mjs` exits 3, no `stopped.txt`) reads "Stopped: Estimate: ..." from the last `estimate` decision event (`estimateStop`) with no phase marked failed; a later `go` decision or any `<Phase>.done` or `long/*.log` newer than the event's `t` clears it. A phase reads running while `lastActivity` (events, logs, markers and files two levels inside `inventory/ inventory-areas/ parity/ score/ report/ rebuild/`) is under 10 minutes old.
- Tests: `node --test scripts/events.test.mjs scripts/watch.test.mjs`.
